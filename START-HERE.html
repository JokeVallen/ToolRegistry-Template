加一个工具

Six actions per tool: build the artifact, place it, describe it, regenerate the catalog, validate, commit. The manifest and its artifact change together or not at all.

这一步的目标：payloads/ 下多一个能通过校验的工具。

最省事的起点是复制示例：

方式 A：保留模板作为上游（以后能拉取改进）

  • 可钉住：使用者可以按 tag / commit 取，装出来的东西是确定的。

三个角色与一条边界

A registry of data, an import tool of logic, and a project that is the only thing written to. There is no install logic in the registry and no tool knowledge in the importer.

这一步的目标：说清 Registry / 导入工具 / 工程各自负责什么。

Registry（数据）

每个工具一个 payloads/<id>/tool.yaml，加它指向的不可变制品。没有安装逻辑。

ToolImport（逻辑）

解析、校验、依赖求解、写盘、回执、卸载。它不知道具体有哪些工具。

你的工程（唯一被写的）

装了什么记在 Library/ToolImport/receipts/，卸载按回执删。

两者之间只有一份数据契约与一份 JSON Schema。契约不变，任一侧都能单独替换——这也是为什么 “前端坏了还能用 CLI 装”成立：编辑器里的 C# 编译不过时，CLI 仍然能跑。

四条约束带来的价值

  • 可审阅：装的是人类读得懂的清单，不是不透明的大包。
  • 可复现：size 与 sha256 在写盘前校验。
  • 可卸载：回执记录每个文件的来源。
  • 可跨引擎：一个工具可以同时给 Unity 与 Godot 提供落点。

典型场景

  • 把散落的复用代码做成“可安装清单”，而不是聊天记录里的压缩包。
  • 一个工作区多个工程共用同一批库，升级只改一处版本号。
  • 交付一包带依赖关系的能力，而不是一个巨大的 .unitypackage。
  • CI 里校验“这份清单还能不能装”，不需要启动编辑器。
