# 编辑器前端设计文档 / Editor Front-End Design

> 本文面向前端（Unity 编辑器窗口）的后续迭代。它记录**为什么这样设计**、**哪些是承诺**、
> **哪些可以改**，以及**明确的边界**。改动前请先读第 2 节与第 6 节。

## 1. 这个前端是什么

一个 Unity 编辑器窗口：浏览注册库、审阅安装计划、安装与卸载。

后端是一个 Node CLI（`utool`）。前端**只负责显示与转发**，不含任何格式逻辑。

## 2. 一条不可动摇的分工原则

**所有可能出错的判断都在 Node 里，前端一个都不做。**

| 判断 | 归谁 |
| --- | --- |
| 解析 `.yaml`、校验 schema | 后端 |
| 解析依赖、选版本、检测环 | 后端 |
| 校验 sha256、决定安装顺序 | 后端 |
| 记录回执、引用计数、卸载边界 | 后端 |
| 画界面、收集点击、显示结果 | 前端 |

**为什么**：Unity 工程一旦有编译错误，编辑器程序集**不会加载**，这个窗口**根本打不开**。
所以它不能承担任何关键职责——否则"工程编译不过"会同时导致"工具无法修复工程"。
命令行始终可用，这条后路是有意保留的。

> 推论：前端**永远不要**自己去读 `.yaml`、算 hash、或猜依赖。需要新信息就让后端
> 多输出一种 record。

## 3. 前后端契约

前端用 `--records` 模式，不用 JSON：`UnityEngine.JsonUtility` **无法反序列化根级数组**，
而在编辑器里手写 JSON 解析器等于把后端的活重做一遍且更容易错。

格式：`TYPE \t field \t field ... \n`，字段转义 TAB/CR/LF。首条记录是
`META recordsVersion <n>`，供前端判断自己是否读得懂这次输出。

前端已使用的 record：

| record | 用途 |
| --- | --- |
| `META recordsVersion` | 契约版本 |
| `TOOL` | 工具列表（`list`） |
| `VERSIONS` | 该工具发布了哪些版本 |
| `TARGET` | 每个引擎一组：依赖门槛、制品类型 |
| `DETAIL` / `DEPENDENCY` / `WILLINSTALL` | 详情（`show`） |
| `PLANTOOL` / `PLANFILE` / `PLAN` | 计划与校验结果（`plan`） |
| `INSTALLED` / `INSTALLEDFILE` | 安装结果 |
| `REMOVED` / `REMOVEDDIR` / `RECEIPTREMOVED` | 卸载结果 |
| `RECEIPT` | 已安装清单（`status`） |
| `PROBLEM` / `ERROR` | 失败原因 |

**改字段顺序 = 破坏契约。** 追加字段或新增 record 类型是安全的（旧前端会忽略）；
删除或重排必须同时提升 `recordsVersion`，并更新 `apps/cli/lib/records.js` 的注释。

**踩过的坑**：`PLAN` 是**一条记录里塞多个键值对**（`PLAN tools 2 bytes 2968 ok true`），
不是 `RESULT key value`。曾按"第一个字段等于 ok"去匹配，永远匹配不到，
于是**校验通过的计划显示成"未能验证"**。读这类记录必须按键值对扫描，不能假定位置。

## 4. 界面结构

```
┌──────────────────────────────────────────────────────────────┐
│ [Refresh] [Registry: ToolRegistry] [Settings...]  [搜索] │
├────────────────────────┬─────────────┬───────────────────────┤
│ [All ▾]            3/5 │             │ Tool Name [installed] │
│ ══════════════════════ │             │ id (可复制)            │
│ ● Guard Utils    1.1.0 │             │ version • type        │
│ ○ Selection History    │             │ Homepage Doc Notes MIT│
│                        │             │ Engines               │
│                        │             │   - unity             │
│                        │             │ Provides              │
│                        │             │   - script.api.x      │
│                        │             │ Dependencies (可跳转)  │
├────────────────────────┴─────────────┴───────────────────────┤
│ Install into [________________] [Default]                     │
│ [Verify and plan] [Install] [Uninstall...]                   │
└──────────────────────────────────────────────────────────────┘
statusMessage
```

- **顶部工具栏**：刷新、**只读的**注册库指示（点击打开设置）、设置入口、搜索
- **左栏**：右对齐的折叠控件、筛选（一行；需要取值时多一行）、分隔线、工具列表；
  **在某个工具行上右键**选择版本
- **折叠后的左栏**：一条窄栏，只放把它展开的按钮；位置仍在列表原来的地方，
  这样"撤销某个动作的控件"就待在那个动作发生的位置
- **竖线**：列表与详情之间
- **右栏**：详情；链接（`Homepage`、`Documentation`、`Release notes`，以及**只写名字**的
  许可证——`MIT`，而不是 `License: MIT`）在身份块下方排成一行
- **安装落点**紧贴按钮上方：改它的后果就在旁边（改掉会让下方那份计划失效）
- 列表项前缀：`●` 已安装 / `○` 未安装；`[no unity]` 表示本引擎不支持

**计数只出现一次**（筛选行）。之前它同时出现在顶栏右端、筛选行右侧、左下角状态栏——
同一个数字出现三遍，读起来像三件不同的事。**状态栏只报"动作的结果"，
不重复屏幕上已有的状态。**

**为什么搜索在顶栏、筛选在左栏**：搜索框是人会去顶栏找的东西；
筛选读起来像是列表的标题。两者位置不同是有意的。

**为什么列表项不是按钮**：按钮**居中**绘制文本并带内边距，
于是短名字和长名字起始位置不同，看起来参差不齐。列表里每个名字必须**左对齐**。

**选中高亮必须自己画。** 曾经把 `EditorStyles.label.onNormal.background` 拿来做选中背景——
**普通 label 的 on 状态没有背景**，所以复制到的是 `null`，选中行与其它行**逐像素相同**，
点击工具看起来毫无反应。现在直接保留矩形、填色、再画文字，
**不依赖任何样式内部字段**，因此不会以同样方式再次静默失效。

### 4.1 设置单独成窗

配置（注册库位置、CLI 路径、Node 路径）在**独立窗口**里，
主界面顶栏只留一个只读指示和一个入口。

**理由**：配置与工具列表争抢横向空间，而今后每加一个设置都会再争一次。
分开之后，**新增设置不可能影响主界面布局**。

路径存 `EditorPrefs`（**按用户、按机器**，不进工程）：指向某个 checkout 的路径
是这台机器的属性，提交进版本库会破坏其他人的环境。

设置窗口会**显示"自动解析当前找到了什么"**——否则"留空即自动"就只能靠猜。


### 4.1 详情页的可读性原则

| 原则 | 做法 |
| --- | --- |
| 可复制的值要能复制 | id、URL、哈希、路径用 `SelectableLabel` |
| 多值是**列表**，不是一行 | `Engines`/`Provides`/`Injects`/`Tags` 各是一个标题，加一段多行的 `- 值`。芯片试过、已撤掉：一个能力名比两个芯片之间的空隙还长，于是会从词中间折行，读起来像一个字符串。多行放在**同一个标签**里而不是一项一个控件：竖直布局会在每个控件之间留间距，五项就变成五段 |
| 能点的要能点 | 主页、文档、版本说明、许可证都是**链接**，**悬停显示目标地址**，彼此用 `·` 分隔；许可证**只写名字**——一行四个链接里，`License:` 前缀会让它读起来像一个带标签的字段；依赖项是可点击的行，默认选中第一个 |
| 可滚动的区域要看得见东西 | 依赖列表给显式高度——在详情页的滚动视图里，`ExpandHeight` 没有可扩展的父高度；计划里的长路径放进**横向**滚动视图，否则文件名正好被裁掉 |
| 能输入的地方要看得出来 | 搜索框设置**文本光标**；链接设置**链接光标** |
| 空值也要显示 | `- (none)` 而不是省略该节——"没有"本身是信息 |
| 约束说人话 | `^1.1.0` → `1.1.0 or newer (same major)` |
| 区域要能分开 | 工具栏 / 左栏 / 详情 / 按钮之间画分隔线 |
| 写之前就能看见落点 | 按钮上方一个 `Install Into` 标题行 + 输入框，留空表示"按清单声明"，空状态写在**框内**，完整规则放在标题的**悬停提示**里；`Browse...` 用目录面板选，选完转成工程相对路径 |
| 声明清单与计划不重复画 | 有一份有效计划时不再画"Installs N file(s)"：计划列出的是最终落点（含依赖、含 `--into` 迁移），声明清单只是承诺。没计划时才画，作为预览 |
| 被移动过的工具要报出来 | 卸载时记录里的文件全都已不在原处，状态栏就点名那个已不存在的目录，而不是报"0 个文件被移除" |

### 4.2 搜索

在**显示名**上做不区分大小写的**子串**匹配。

**只搜显示名**，不搜 id、type、tag、provides。原因是一个真实反馈：
输入 `s` 会命中 `gITF Importer`，因为它的 **id 是 `libs-gltf-importer`**。
**匹配是真的，但屏幕上没有 id——用户看不见的东西被匹配了，这和坏掉无从区分。**
tag 与能力的筛选由独立控件承担（见 4.3），它会明确说明自己在筛什么。

**为什么不加防抖：因为没有可防的抖。**

过滤是内存中几个小字符串的子串扫描，成本是**微秒级**。加防抖要引入计时器、
重绘依赖，并且让结果**慢一帧**——用真实的复杂度去掩盖一个不存在的开销。

真正该做的是**不要每帧重算**（见 4.4），而这个触发条件是**实测到的成本**，
不是"用户正在打字"这个事实。

### 4.3 筛选

`Show:` 下拉框。前四项是固定子集：

| 选项 | 含义 |
| --- | --- |
| All | 全部 |
| Installed | 已安装 |
| Not installed | 未安装 |
| This engine | 本引擎有 target 的 |

后四项各需要**一个取值**，由第二个下拉框选：`Tag is`、`Provides`、`Injects`、`Depends on`。

**为什么是下拉而不是多个独立开关**：两个独立开关可以同时打开，产生
"既已安装又未安装"这种没有意义的状态，用户还得自己判断当前处在哪个组合里。
**单选不可能自相矛盾。**

**为什么取值列表取自列表本身、而不是手输**：第二个下拉框只能列出确实存在的取值，
所以拼错不会静默产出一个空列表。这与后端 `--provides` 的提示是同一类问题；
而前端本来就持有列表，不需要为此多发一次请求。

**`Depends on` 是反查**：它回答"删掉这个会坏什么"。列表能直接回答，因为 `TOOL`
记录了每个工具的依赖 id。

tag 与能力的匹配是**逐元素精确匹配，不是子串**：tag 为 `editor` 不应选中
标了 `editor-tool` 的工具。子串匹配在数据上说得通、在界面上是错的——
这与"搜索命中了用户看不见的 id"是同一种失败。

`This engine` 只判断"本引擎有没有 target"，**不判断能否安装**——后者需要
`TARGET` 记录的制品类型，那要每个工具发一次 `show`，代价是每个工具一次后端调用。

### 4.3a 版本选择

一个工具可能发布多个版本。**版本选择跟着工具行走**：在某个工具行上右键，版本在**一级菜单
`Versions`** 下作为二级菜单。这是唯一的控件。

- **为什么放二级菜单。** 行菜单是"这个工具的每个动作"该去的地方。把版本摊在一级，等于用整张
  菜单说一件事，之后再有动作（卸载、复制 id、打开回执……）就只能挤到版本列表旁边，或者让菜单
  每加一条就重排一次。一级留一个 `Versions`，扩展空间是结构性的，不是靠排序凑出来的。
- **为什么放在行上、不放详情页。** 详情页的内容是**按版本**的——换版本，描述、门槛、制品都会
  换——所以版本列表放在详情页里时，它正压在一段"点一下就会被替换掉"的文字下面。选版本实质上
  是**选要看哪一条记录**，那就该待在这条记录的名字旁边。
- **为什么只给右键菜单。** 行内展开的版本列表试过、已撤掉：它与菜单重复，会把列表列撑得高度
  不可预测，而且把一个"按版本"的控件塞进了描述"工具"的那一列。右键是一个手势，且用过文件列表
  的人本来就会往那儿找——所以界面把这个手势**说出来**（见下），而不是再加第二个控件。
- **菜单同时给出两件事**：勾选标记是**当前钉住的**版本，` • installed` 标的是工程里**实际装着的**
  那一版。两者在"有更新可用"时正好不同，而那正是需要区分的时候："选中"单独一个标记会让被勾选
  的那项看起来就是已安装的那项。
- 选中结果以 **`id@version`** 保存，并且**属于所选的那个工具**。切换到别的工具会丢弃它，
  因为 `0.9.0` 对一个从未发布过该版本的工具毫无意义。
- 详情会**按选中的版本重新拉取**，因为描述、门槛与制品都可能随版本不同。
  把 latest 的元信息和一个旧版本的安装计划并排显示，比什么都不显示更糟。
- `show`、`plan`、`install` 都带上这个引用，所以**描述的是哪个版本，装的就是哪个版本**。
- 与选中项一样存在 `SessionState`，因此重新编译不会把用户悄悄从所选版本挪回 latest。

**手势要明说。** 右键菜单没有任何可见的提示，所以标题行会讲：已安装但落后于 latest 的工具显示
"右键这个工具选择升到哪个版本"。**"发布了 N 个版本"那句话已撤掉**：它先报一个数、再说一个手势，
而手势本来就写在菜单里；每多一个发布过多次版本的工具，它就要占一行。

**一次只跑一个后端调用，等待中的以最新为准。** 面板一次只显示一份详情，所以前一次调用还在跑时
发起的请求要排队，并且**新请求覆盖等待中的旧请求**——否则钉住的版本已经变了，屏幕上却还是上一版
的内容（"选 0.9.0 显示 1.0.0"就是这个）。超时或被取代的请求不该把旧结果画回去。

**已安装的版本也要说出来。** 只显示"已安装"回答不了版本选择器真正引出的问题——
**装的是哪个版本**。因此徽标写成 `installed 1.0.0`，菜单标出已安装的那一版，
并且当已安装版本不是 latest 时**明确说明"有更新"**，而不是让用户自己在两处比对两个版本号。

**版本说明只给链接，不做面板。** 更新日志是在**发布之后**继续维护的，抄进注册库的副本
会在"正要决定要不要升级"的时候正好过期；而且前端没有数据，本来就渲染不出更新日志。
`releaseNotes` 是一个 URI，界面只显示一个 `Release notes` 链接。原来的 `What changed`
因此删除——它是这个工具里唯一一处在"宁给你旧副本，也不给你源头"的地方。

### 4.4 性能

IMGUI **每次鼠标移动都会重绘**，所以每帧的成本会被放大。已做的处理：

- **过滤结果每帧只算一次，且仅在输入变化时才重算。** 之前工具栏（算计数）和列表
  各调一次 `VisibleTools()`，于是每次重绘都完整过滤两遍、分配两个 `List`。
  现在按 `OnGUI` 每帧算一次，并用（搜索词、筛选、**筛选取值**、工具数）作为缓存键。
  取值也是键的一部分：只改取值（`editor` → `workflow`）而模式没变，否则屏幕上会留下旧列表。
- **已安装集合变化会使缓存失效**，否则刚装完的工具不会出现在 `Installed` 里。

**已知的、故意的取舍**：列表行用显式矩形绘制（不再是 `GUILayout.Toggle`），每行每次重绘都构造
一个 `GUIContent`。工具数量是**几十**量级，这是可接受的；若将来达到**上千**，
再考虑虚拟滚动（只画可见行）——届时触发条件是**实测数量**，不是预防性优化。

**状态串行而不是并发**：`Run` 用**一个** `busy` 标志串行所有后端调用。
这是有意的（避免并发写同一工程），但**调用方必须自己排队**——见 4.5。

### 4.5 单标志串行带来的调用约定

`Run` 持有一个 `busy` 标志，**在其为真时直接返回、什么都不做**。

**这个 bug 修了两次才对，值得记下来。**

第一次诊断是错的：我以为 `OnEnable` 里两个并列调用（`RefreshInstalled()` 然后 `Refresh()`）
互相竞争。改成回调串联后**症状依旧**。

真正的原因更隐蔽：**回调是在 `Run` 内部、`busy` 仍然为真时执行的**。
`busy = false` 写在 `finally` 里，而 `onSuccess(records)` 在它**之前**。
所以"回调里再发起一个调用"——无论写成回调还是并列——**一样被丢弃**。
换了个形状，碰撞没变。

**约定**：

1. **绝不在一次调用仍在进行时发起下一次。** 需要顺序执行就用 `QueueCommand(...)`，
   它把工作推迟到 `finally`（`busy` 刚被清除的那一刻）。
2. **busy 期间必须禁用控件**，否则点击被静默吞掉。列表行现在 busy 时禁用——
   **点了没反应比点了不可用更糟**。
3. 队列是**单槽**的：一连串点击只会保留最后一个，因为更早的请求到执行时已经过期。

```csharp
// 正确：推迟到 finally
QueueCommand(() => RefreshInstalled());

// 错误：回调里直接调用 —— busy 仍为真，被静默丢弃
RefreshInstalled();
```

### 4.3 已确定的交互约束

- **引擎选择器已移除。** 这个窗口**就是** Unity 编辑器，而选择器曾允许把 Godot 插件
  装进 Unity 工程（后端引擎无关，照单全收）。**UI 只能提供它能兑现的选项。**
- **不支持的工具禁止安装。** `external`/git 类型的目标，后端只报告、不解析，
  安装会"看起来成功却什么都没写"。因此 `Verify and plan` 与 `Install` **禁用**，
  并在详情页与按钮上方各给一次**醒目**说明（`Warning`，不是 `Info`）。
  **但 `Uninstall` 不禁用**——已经装上的东西必须始终能卸掉，否则用户被困住。
- **Targets 只显示本引擎。** 其他引擎的目标**如实说明但不可操作**：
  `Also ships a target for: godot (not installable here)`。完全隐藏会造成与
  `utool show` 输出不一致。
- **Uninstall 仅在已安装时可用。** 未安装时按钮禁用并显示 `Uninstall (not installed)`；
  可点击却只能报错，会被读成"工具坏了"而不是"这个没装过"。
- **列表按会话缓存。** Unity 关闭窗口会销毁 `EditorWindow`，若不缓存则每次重开都要
  Refresh → 重选 → 重新 Verify。`Refresh` 仍可手动重读；**刷新失败不得用空列表覆盖好数据**。
- **破坏性操作必须二次确认**，且说明后果（装/卸载各自一个对话框）。
- **空列表要区分两种空**："注册库没有工具"与"没有匹配当前搜索/过滤"原因不同、改法不同。

## 5. 样式与 UI 框架

**现状：IMGUI（`EditorGUILayout`）。** 理由：零依赖、单文件、无需构建步骤、
在任何 Unity 版本上行为一致。

**已记录的改进方向：UIToolkit（UIElements）。** 用户在迭代中提出过，理由成立——
性能更好（保留模式，不重建控件树）、样式更佳（USS）、布局能力更强。

**但迁移不是免费的**，代价必须先说清：

| 项 | 影响 |
| --- | --- |
| 现有窗口全部重写 | 约 700 行，逻辑与显示目前是混在一起的 |
| 版本门槛 | `minEngineVersion` 目前是 `2019.4`；UIElements 稳定可用性更好是在 2021+ |
| 测试方式改变 | 现在靠类型检查 + 行为测试，UIElements 需要新的验证手段 |

**建议的迁移路径**（不要在没做第 1 步前动手）：

1. **先把逻辑从显示里分离**——`BackendRecords` 已经是纯逻辑且**可执行测试**，
   继续沿这个方向把"状态"与"渲染"拆开；
2. 再换渲染层，此时换 UI 框架的风险才可控。

> 目前**不承诺**迁移时间。它是一个有明确前置条件的方向，不是一个待办事项。

## 6. 目标版本与范围（这是承诺）

**稳定目标：`v1.0` —— 当前功能集冻结，之后只做修复。**

`v1.0` 包含（**全部已实现并有测试**）：

- 浏览注册库、查看工具详情与依赖
- 解析依赖并给出安装计划
- 校验制品（size + sha256）后才写入
- 安装 / 卸载，含回执、引用计数、空目录清理
- 卸载被依赖的工具时**默认拒绝**，`--force` 可越过
- 孤儿依赖**只报告不自动删**

**明确不在 `v1.0` 范围**（写在文档里而不是含糊带过）：

| 项 | 状态 |
| --- | --- |
| `external` / git 类型真正去 clone | **不实现**，界面**禁用**并说明 |
| rollback 真正回滚字节 | **不实现**，只报告指针 |
| UIToolkit 迁移 | **不做**，兼容性优先，继续用 IMGUI |
| 安装路径由使用者覆盖 | **v1.1 才做**（见下） |
| 多引擎前端 | 后端支持；只有 Unity 前端 |

**`v1.0` 之后还会加功能吗？** 会，但遵循一条规则：**只加不破坏**。
新增 record 类型、新增可选字段、新增引擎适配器都允许；改变已有语义需要新的大版本。

### 6.1 版本规划（这是路线，不是承诺日期）

**`v1.0` —— 界面成形 + 已实现功能的诚实呈现**

### 6.2 落点归属：已实现

**使用者说得对**：项目布局因项目而异，工具不该单方面锁死路径。而实现时技术事实改写了当初的
设想——三处不一样：

| 当初的设想 | 现在实际的做法 | 为什么 |
| --- | --- | --- |
| 新增 `suggestedRoot` 字段 | 不加字段：清单里的 `contentRoot` / `targetPath` **就是**建议落点 | 再声明一个根，等于同一件事有两个来源；两者一旦不一致，写出去的文件就会落在使用者所选目录之外 |
| 由清单给出"根" | 由**实际落点反推**根目录（所有落点路径的公共目录） | 与上一条同一个理由：唯一事实来源是"文件到底落在哪" |
| `unitypackage` **不能**重定位 | **可以**：适配器把每项的 `pathname` 报给核心，并经由写入上下文落盘，改写发生在那一处 | 目的地是打包时烧死的没错，但**写入**这一步仍由核心决定路径 |

现在的行为：

1. **默认按清单。** 清单声明的落点就是默认落点，使用者什么都不填时行为与以前完全一致。
2. **使用者可覆盖**（`utool install --into <目录>`，或界面按钮上方那个 `Install into` 字段）。
   覆盖按"替换那个根"生效，**根以下的结构完整保留**。
3. 回执记录**实际**根目录（`installedRoots`），所以卸载与引用计数不需要再被告知一次。
4. 只作用于**点名要的那个工具**：依赖保持自己的布局。`--into` 因此要求恰好一个 id。
5. 路径对不上就**拒绝**（`E-INSTALL-ROOT`，什么都不写），而不是按前缀算到哪儿是哪儿。
6. 覆盖值非法（空、绝对路径、盘符、`..`）在**取制品之前**就报 `E-INSTALL-INTO`。

> 判据没变：**能重定位就重定位，不能就明确拒绝**——最坏的结果是"以为改了却没改"。
>
> 另一半也补上了：**工具目录被移动之后卸载**，回执里每一条路径都已不存在，于是"卸载成功"
> 却什么都没删。这种情况现在会点名那个已不存在的目录（`MOVEDROOT`），并且**仍然不去删**它——
> 一个被拖走的目录与一个使用者自己建的目录，从数据上无法区分。

## 7. 与 UPM 的关系（重要：先把话说直）

**UPM 是官方方案，更成熟，能覆盖本工具的一部分用途。** 如果需求完全落在下表"UPM 可以做"
那一列，**就应该直接用 UPM**。

| 能力 | UPM | 本工具 |
| --- | --- | --- |
| 从 git URL 安装 | ✅ 原生 | ⚠️ 只报告 `external`，不 clone |
| 从本地目录 / tarball | ✅ | ✅ |
| 依赖声明与解析 | ✅ 完整 semver | ✅ 含能力注入 |
| 版本范围 | ✅ | ✅ |
| **非 Unity 引擎** | ❌ Unity 专有 | ✅ Godot 同源发布 |
| **共享运行时源码给两个引擎** | ❌ | ✅ 同一份 C# |
| **任意制品形态** | ⚠️ 主要面向包目录 | ✅ unitypackage / tgz / 裸 dll / 外部源 |
| **能力级依赖**（`injects` / `provides`） | ❌ | ✅ |
| **安装前逐字节校验** | ⚠️ 有 hash 但非本模式 | ✅ size + sha256，不匹配就拒绝 |
| **精确卸载** | ⚠️ 移除包目录 | ✅ 回执 + 引用计数 |
| **引擎版本/运行时门槛** | ⚠️ 有限 | ✅ 三值判断（不可判 = 报告而非阻止） |

**结论（不含推销）：**

- 若你**只做 Unity、只用标准包**，UPM 更好。它免费、官方、没有本工具的后端依赖。
- 本工具的价值主张是**跨引擎 + 能力级依赖 + 安装前校验 + 精确卸载**这四点。
  如果这四点对你都不重要，**应该用 UPM**。
- 本工具**不与 UPM 竞争**。`libs-gltf-importer` 这类 `external` 条目的
  `upmPackageName` 字段正说明二者的关系：注册库可以**指向**一个 UPM 包，
  而不是取代它。

> 诚实说明：本工具比 UPM **少**大量的成熟度——没有官方支持、没有大规模验证、
> C# 前端**从未在真实 Unity 中运行过**（见第 8 节）。把它当作一个有的放矢的
> 补充手段，而不是 UPM 的替代品。
